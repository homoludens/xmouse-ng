## Purpose

Provide the approved native three-destination remote-control interface while preserving real SSH behavior and existing hosts, protected credentials, actions, scripts, layouts, and preferences.

## ADDED Requirements

### Requirement: Native three-destination shell and truthful header
The application SHALL provide Touchpad, Keys, and Actions bottom destinations and a header showing the selected computer, actual connection state, and settings. The computer control SHALL open computer selection/management. Navigation SHALL NOT disconnect a healthy session or execute a remote command merely by changing destinations.

#### Scenario: Navigate with a healthy session
- **WHEN** the user changes between the three destinations and returns to Touchpad
- **THEN** the same authenticated session SHALL remain available and the selected destination SHALL be identifiable
- **AND** no pointer/key/script command SHALL be generated by navigation alone

#### Scenario: Connection is not yet ready
- **WHEN** a connection is preparing, connecting, awaiting trust, authenticating, failed, or disconnected
- **THEN** the header SHALL show the real state rather than claim success
- **AND** a deliberate reconnect or computer-management path SHALL remain available

### Requirement: Accessible system-following visual design
The application SHALL use the handoff's semantic light/dark palettes, native typography and controls, readable labels, and at least 48 by 48dp effective touch targets. Controls SHALL remain reachable around system bars, cutouts, and the IME, at approximately 320dp width and enlarged font sizes. Browser reference code and fake device chrome SHALL NOT be used as application UI.

#### Scenario: Theme, narrow width, and keyboard
- **WHEN** the device uses either system theme, a narrow display, enlarged text, or a visible keyboard
- **THEN** header, navigation, forms, labels, and action controls SHALL remain readable and reachable without overlapping system UI

### Requirement: Preserve gesture and alternate-input behavior
The Touchpad destination SHALL provide a dominant pointer surface, scrolling, left/middle/right click, common quick keys, and labeled typing access. Existing drag/hold, gyro, joystick, and volume shortcuts SHALL remain accessible. Leaving an eligible input surface SHALL cancel stale gestures and release tracked held inputs when possible without replaying old input on return.

#### Scenario: Leave during a drag
- **WHEN** a user changes destination or opens a computer/settings/editor overlay during a held pointer gesture
- **THEN** the old gesture SHALL be invalidated and its held input released when the session permits
- **AND** returning SHALL require a new gesture rather than resume stale input

### Requirement: Explicit phone-keyboard typing and clipboard export
Type on computer SHALL use the real Android keyboard, a labeled text field, explicit Send, and Esc/Tab/Backspace/Enter controls. Text encoding and escaping SHALL preserve non-ASCII characters and literal input. The deliberate one-way clipboard export SHALL remain accessible, without background clipboard reads or automatic pasting.

#### Scenario: Type literal text
- **WHEN** the user enters Unicode, quotes, whitespace, or shell-like text and presses Send
- **THEN** the entered text SHALL be dispatched through the existing typing behavior without being reinterpreted as an additional command
- **AND** opening or editing the typing field alone SHALL NOT send its contents

### Requirement: Categorized keys and honest media controls
Keys SHALL offer Common, Navigate, Media, and F1–F12 categories covering the existing supported shortcuts. Media and brightness controls SHALL use supported relative adjustments and mute rather than invented absolute levels or decoration-only polling.

#### Scenario: Adjust volume and brightness
- **WHEN** the user activates a relative media or brightness control
- **THEN** the corresponding existing command SHALL be dispatched
- **AND** the interface SHALL NOT report an unobserved percentage or unsupported absolute value

### Requirement: Real computer management and non-destructive authentication edits
Computer selection, adding, editing, finding, connecting, disconnecting, and confirmed deletion SHALL operate on real persisted data and existing authentication methods. Forms SHALL use persistent labels and preserve hostname, username, actual SSH port, and untouched credentials. A blank replacement password for an existing computer SHALL mean unchanged and SHALL NOT store a placeholder or erase the saved secret. Invalid input SHALL leave the form open and valid stored values unchanged.

#### Scenario: Edit metadata without replacing a password
- **WHEN** a user edits a saved computer's name or port and leaves its replacement password blank
- **THEN** the non-secret changes SHALL persist while its existing protected credential remains usable
- **AND** the application SHALL NOT decrypt the saved password merely to fill the editor

#### Scenario: Invalid or accidental username whitespace
- **WHEN** an entered host/port/username is invalid or the username has accidental leading/trailing whitespace
- **THEN** the form SHALL identify the field and retain the user's input for correction without overwriting a valid saved computer

### Requirement: Truthful bounded connection testing and discovery
Connection testing SHALL test the entered candidate using real SSH/trust/authentication behavior, without silently saving it, running an initial command/script, or replacing an active control session. Test work SHALL be bounded and cancellable with form lifecycle, and discovery SHALL show actual results or actionable empty/error states rather than sample computers.

#### Scenario: Test an unsaved candidate
- **WHEN** a user requests Test connection before saving a computer
- **THEN** success SHALL be shown only after the real authentication/channel check succeeds
- **AND** failure/cancellation SHALL leave saved computers, credentials, and any active control session unchanged
- **AND** host-key approval requirements SHALL remain in force

### Requirement: Persisted Actions and scripts with compatible semantics
Actions SHALL show actual named layouts, custom buttons, and saved scripts; provide explicit Edit/Done, create/edit/delete, layout selection/management, and access to ordering/history. New Regular/Wide and color presets SHALL be conveniences without converting untouched legacy values. Shortcut, advanced custom-command, and raw-script meanings SHALL remain distinct, and editing SHALL NOT execute a command.

#### Scenario: Save an existing custom action unchanged
- **WHEN** a user edits an action with a custom width, RGB color, or legacy xdotool command without replacing those values
- **THEN** its identity, layout association, order, width, color, and command meaning SHALL survive saving and restarting
- **AND** editing, selection, or preview SHALL NOT execute it

#### Scenario: Run a saved script
- **WHEN** a user deliberately runs a saved script from Actions
- **THEN** the existing script execution route SHALL run its persisted command and report actual success/failure behavior
- **AND** the script SHALL NOT be silently converted into a custom-button command

### Requirement: Working persisted settings without demo state
Displayed pointer/scroll/input settings SHALL bind to working saved preferences and survive restart. Unsupported preview-only settings SHALL be omitted unless their behavior is implemented. The application SHALL NOT seed user data with the reference's example computers, scripts, buttons, layouts, or media levels.

#### Scenario: Change a real input setting
- **WHEN** the user changes pointer speed or natural scrolling and restarts the application
- **THEN** the saved value SHALL be restored and used by actual input dispatch
